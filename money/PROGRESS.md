## Service API as built
Every write takes a caller-supplied `ref`; a retry with the same ref and same content is `{ dup: true }`, different content throws `ref_conflict`. Funds are `'chips'` (bank) or `'play'` (wallet); `'bank'` is accepted as an alias of `'chips'`; missing/null = the table's own currency (today's `fundOf`), anything else throws `bad_fund`.

```
createService(ledger, { now })
ensureAccount(key)                                   -> { created, minted }   mints only the currency that has no account yet; refs signup:bank:<k>, signup:play:<k>
buyIn(key, tableId, amount, tableCur, fund, ref)     -> { id, dup }           same currency = one transfer, else one batch through fx:<cur>
cashOut(key, tableId, amount, tableCur, fund, ref)   -> { id, dup }           amount 0 = { noop: true }; moves the stack only, committed stays in the seat
settleHand(tableId, handNo, tableCur, { committed, payouts, returned })
                                                     -> { id, dup }           ONE batch, ref hand:<t>:<n>; not_conserved throws before anything is written
mint(kind, key, amount, cur, ref)                    kind = bonus | achv | topup
houseSpend / houseCredit(game, key, amount, cur, ref)   game = bender | coldcall
adminAdjust(key, delta, cur, reason, ref)            signed delta, bank/play only, insufficient throws (no "set total")
topUpEligible(key)                                   -> { eligible, why: null|'not_needed'|'cooldown', total, wallet, seats, retryMs }
topUp(key, ref)                                      convenience over mint('topup'): brings wallet + Play seats back up to 1,000,000
bootRecover(bootId)                                  -> { seats[], pots[], errors[] }   refs boot:<bootId>:<account>
mirror()                                             -> { bank: {key: n}, wallet: {key: n} }
nightSummary(tableId, { fromId })                    -> { perKey: { k: { buyIn, cashOut, open, net } }, zeroSum, sum }
balances(key), seatFund(tableId, key, cur)           helpers
```

Ledger reasons used: `buyin:<fund>`, `cashout:<fund>`, `boot:<fund>`, `boot:pot`, `hand`, `signup`, `bonus|achv|topup`, `bender:spend|credit`, `coldcall:spend|credit`, `admin:<text>`, `migration`, `migration-mark`. The seat's fund is read back from the most recent `buyin:<fund>` entry into that seat, so `bootRecover` needs no memory.

## Things in the contract that are wrong, unclear or that I extended
1. Service signatures in the brief have no `ref` parameter but the same brief says every op takes one. I added `ref` as the last argument (settleHand, bootRecover, ensureAccount derive theirs).
2. `stacks.json` as written by `server.js saveStacks` is flat `{ key: chips }` with no table id, but the contract says ref `mig:stack:<table>:<key>`. Flat input uses table `all` (`mig:stack:all:<key>`); the nested `{ table: { key: n } }` form is also accepted.
3. Zero balances cannot be written (amount must be positive), but the old server mints 10,000 for a bank row that is missing, so a zero-balance account must still exist. Migration registers zero and rejected rows with a zero-net batch (`mint:migration -> acct 1`, back 1, ref `mig:bank:<k>`). Without it `ensureAccount` and the rollback `mirror()` would give those accounts free money.
4. A rejected row (non-integer, negative, wrong type) leaves the account at 0 and is listed; it does NOT get the lazy default on top. Chris fixes it with adminAdjust. Rejected rows for keys that are not accounts create nothing.
5. An account with a stack but no bank row gets no default (today's boot makes the row from the stack). The contract's "no bank row -> default" would add 10,000 on top.
6. Orphan refs are not in the contract: `mig:orphan:chips:<name>`, `mig:orphan:play:<name>`, `mig:orphan:stack:<table>:<name>`. Bank rows match accounts by exact key only (`Raj` does not match `raj`; it becomes `orphan:Raj`).
7. Batch lines carry one `ref` (the batch's); items inside have no ref of their own. `entries()` reports the batch ref as both `ref` and `batchRef` for batch items.
8. Top-up: `wallet.js` sets Play to 1,000,000. v2 `topUp` tops wallet + Play seats up to 1,000,000 total (otherwise H7 returns through the amount). `lastTopUp` from wallet.json is not migrated, so every cooldown restarts at migration.
9. Sources are exactly the contract's list. A new game needs `house:<game>` added to `SOURCE_ACCOUNTS` in `ledger.js` and to `GAMES` in `service.js`.
10. Account keys, table ids and hand numbers may not contain `:` (account keys already can't: `NAME_RE`). Orphan names may.
11. `fsync` runs on batches only, as specified. A single transfer (a same-currency buy-in or cash-out) is in the OS cache, not fsynced: safe against a process crash or deploy, not against power loss. `open(file, { fsync: 'all' })` fixes that if wanted.

## Not verified
- Not wired into server.js, tables, sockets or the engine (not my job); the API shapes are tested only by my own tests.
- No real prod data. Fixtures come from the formats in the code.
- No file lock: two processes opening the same `money.jsonl` at once would corrupt it (e.g. an overlapping Railway deploy on a shared volume). Not tested.
- Mixed funds on one seat (rebuy from the other fund): the whole seat returns to the fund of the last buy-in. Per-fund tracking is not built.
- Performance at scale: the ledger keeps every line in memory and `list`/`seatFund`/`nightSummary` scan. Fine for thousands of lines; not measured beyond the 10,000-transfer fuzz and the 500-account fixture.
- `bootRecover` stray-pot refund (pro rata, largest remainder) is tested on one hand-built pot only.
