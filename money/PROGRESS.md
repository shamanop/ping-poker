## Service API as built
Errors (`MoneyError.code`): `bad_amount bad_account bad_cur bad_reason bad_ref bad_item empty_batch insufficient ref_conflict not_conserved fund_mismatch lost_lock foreign_write write_failed closed corrupt`, plus `bad_key bad_table bad_hand bad_fund bad_kind bad_game`.

Every write takes a caller-supplied `ref`; a retry with the same ref and same content is `{ dup: true }`, different content throws `ref_conflict`. Funds are `'chips'` (bank) or `'play'` (wallet); `'bank'` is accepted as an alias of `'chips'`; missing/null = the table's own currency (today's `fundOf`), anything else throws `bad_fund`.

```
createService(ledger, { now })
ensureAccount(key)                                   -> { created, minted }   mints only the currency that has no account yet; refs signup:bank:<k>, signup:play:<k>
buyIn(key, tableId, amount, tableCur, fund, ref)     -> { id, dup }           same currency = one transfer, else one batch through fx:<cur>.
                                                                              One fund per seat: while the seat holds chips (balance > 0) a fund other than seatFund() throws
                                                                              fund_mismatch { have, want } before anything is written; a 0 seat may switch.
                                                                              A retry of a ref already in the ledger skips that check and answers dup.
cashOut(key, tableId, amount, tableCur, fund, ref)   -> { id, dup }           amount 0 = { noop: true }; moves the stack only, committed stays in the seat.
                                                                              The fund is the seat's (seatFund, from the ledger): a different one throws fund_mismatch { have, want },
                                                                              null/missing means the seat's. No buy-in on record = the table currency. A retry of a written ref answers dup.
settleHand(tableId, handNo, tableCur, { committed, payouts, returned })
                                                     -> { id, dup }           ONE batch, ref hand:<t>:<n>; not_conserved throws before anything is written
mint(kind, key, amount, cur, ref)                    kind = bonus | achv | topup
houseSpend / houseCredit(game, key, amount, cur, ref)   game = bender | coldcall

                                                                              same accounts and reasons as the two calls above. The bet is checked first, so insufficient funds for cost
                                                                              throw even when win > cost. win 0 = spend only, cost 0 = credit only, both 0 = { noop: true }.
                                                                              Same ref + content = dup, different = ref_conflict. houseSpend/houseCredit are unchanged.
```

Ledger reasons used: `buyin:<fund>`, `cashout:<fund>`, `boot:<fund>`, `boot:pot`, `hand`, `signup`, `bonus|achv|topup`, `bender:spend|credit`, `coldcall:spend|credit`, `admin:<text>`, `migration`, `migration-mark`. The seat's fund is read back from the most recent `buyin:<fund>` entry into that seat, so `bootRecover` needs no memory.

## Writer fence (ledger.js)
No blocking lock, so a stale lock can never stop a boot. `open()` writes a fresh random token to `<file>.lock` (newest opener wins; replacing an existing lock is logged via `opts.log`, default `console.error`). Before every append the writer (a) re-reads the lock and throws `lost_lock` if the token is not its own, (b) `fstat`s the file and throws `foreign_write` if the size is not the offset it expects (covers growth and shrinkage). Either one makes the writer refuse every later write (sticky). A duplicate-ref retry and reads still work on a fenced ledger. A missing lock file counts as lost. `close()` removes the lock only if the token is still its own; an `open()` that fails with `corrupt` removes its own lock.

Narrow race that remains: the check and the append are not atomic. If a second opener starts between a writer's check and its write, that one line can land. What catches it afterwards: the new opener's next write sees a size it did not expect (`foreign_write`), the old writer's next write sees `lost_lock`, and the next `open()` quarantines the duplicate-id line (below), so it never doubles money and never stops a boot. A quarantined line there is a real money line that did not apply: see the quarantine section.

## Quarantine: a bad line never stops a boot (ledger.js)
`open()` reads the file by bytes and applies every complete line that parses and validates (record shape, amount, accounts, currency, `id` greater than the last applied id, new `ref`, no player account below zero at any step of a batch). Any other line is NOT applied: it is appended once to `<file>.quarantine` as `{ ts, lineNo, reason, line }` (verbatim text), listed in `ledger.quarantined`, counted in `check().quarantined`, and reported with one `log` call (default `console.error`, text starts `QUARANTINED`). The ledger opens on the valid lines and keeps writing. The original file is never rewritten on open, so the same lines are quarantined again next boot and the quarantine file is deduplicated by line text. Only the torn tail (last line without a newline) is truncated, as before. Blank lines are ignored. If the quarantine file itself cannot be written the boot continues and logs it.
- `id` gaps are accepted (only an id that does not go up is rejected). A lost line then costs the lines that depend on it (they fail the overdraft check and are quarantined too), not every line after it.
- New writes take `lastId + 1`, so a quarantined line can share an id with a later valid line. Replay is deterministic (the bad line is evaluated first, in file order), so every boot lands on the same state.
- A quarantined MONEY line means balances may be short by that line (or by what depended on it). That needs an admin look: read `<file>.quarantine`, decide, and apply the fix with `adminAdjust` (never by editing the ledger).

## Things in the contract that are wrong, unclear or that I extended
1. Service signatures in the brief have no `ref` parameter but the same brief says every op takes one. I added `ref` as the last argument (settleHand, bootRecover, ensureAccount derive theirs).
2. `stacks.json` as written by `server.js saveStacks` is flat `{ key: chips }` with no table id, but the contract says ref `mig:stack:<table>:<key>`. Flat input uses table `all` (`mig:stack:all:<key>`); the nested `{ table: { key: n } }` form is also accepted.
3. Zero balances cannot be written (amount must be positive), but the old server mints 10,000 for a bank row that is missing, so a zero-balance account must still exist. Migration registers zero and rejected rows with a zero-net batch (`mint:migration -> acct 1`, back 1, ref `mig:bank:<k>`). Without it `ensureAccount` and the rollback `mirror()` would give those accounts free money.
4. A rejected row (non-integer, negative, wrong type) leaves the account at 0 and is listed; it does NOT get the lazy default on top. Chris fixes it with adminAdjust. Rejected rows for keys that are not accounts create nothing.
5. An account with a stack but no bank row gets no default (today's boot makes the row from the stack). The contract's "no bank row -> default" would add 10,000 on top.
6. Orphan refs are not in the contract: `mig:orphan:chips:<name>`, `mig:orphan:play:<name>`, `mig:orphan:stack:<table>:<name>`. Bank rows match accounts by exact key only (`Raj` does not match `raj`; it becomes `orphan:Raj`).
7. Batch lines carry one `ref` (the batch's); items inside have no ref of their own. `entries()` reports the batch ref as both `ref` and `batchRef` for batch items.
8. Top-up: `wallet.js` sets Play to 1,000,000. v2 `topUp` tops wallet + Play seats up to 1,000,000 total (otherwise H7 returns through the amount). `lastTopUp` from wallet.json is not migrated, so every cooldown restarts at migration.
9. Sources are exactly the contract's list. A new game needs `house:<game>` added to `SOURCE_ACCOUNTS` in `ledger.js` and to `GAMES` in `service.js`.
10. Account keys, table ids and hand numbers may not contain `:` (account keys already can't: `NAME_RE`). Orphan names may.
11. `fsync` default is now `'all'` (every transfer and batch), at the lead's request; the contract said batches only. `'batch'` and `'none'` stay as options for fuzz/bulk. `tools/migrate-v2.js` CLI uses `'none'` plus one `sync()` at the end.

## Not verified
- Not wired into server.js, tables, sockets or the engine (not my job); the API shapes are tested only by my own tests.
- No real prod data. Fixtures come from the formats in the code.
- The fence is tested with two ledgers in one process (and a foreign append by hand), not with two real processes or a real overlapping Railway deploy. The narrow race above is not reproduced by a test.
- `seatFund()` scans the whole ledger per call (boot, buy-in with chips on the seat, cash-out). Fine at today's size, not measured at large sizes.
- A quarantined money line means balances may be short by that line and needs an admin look. It is only reported, never repaired: a lost buy-in or cash-out line can leave a balance short (or a seat unrecoverable) until an admin acts. Nothing alerts anyone beyond the log line and `check().quarantined`; the server layer has to surface it.
- Performance at scale: the ledger keeps every line in memory and `list`/`seatFund`/`nightSummary` scan. Fine for thousands of lines; not measured beyond the 10,000-transfer fuzz and the 500-account fixture.
- `bootRecover` stray-pot refund (pro rata, largest remainder) is tested on one hand-built pot only.
